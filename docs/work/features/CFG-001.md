## Motivo y dependencias

La aplicación tiene AUTH-001, BRANCH-001 y USERS-001 VERIFIED; la tabla `system_configs`, su seeder y el permiso `settings.manage` ya existen. El siguiente slice técnico seguro es administrar exclusivamente los ajustes del **comprobante interno NO tributario**; no implica instalador, DTE, clientes, catálogo, caja o contrato nuevo. Se eligió por depender solo de la infraestructura ya verificada y no requerir decisiones materiales de producto.

- Parte 2 §3.1: `receipt_header`, `receipt_footer` (string opcional, vacío permitido) y `receipt_paper` (solo `58mm`, `80mm` o `A4`; defecto `80mm`).

## Qué implementar (sin inventar reglas)

1. Página administrativa accesible desde Dashboard, p. ej. `/settings/receipt`, para leer y editar **solo** las tres claves anteriores. Menú visible únicamente a `settings.manage`, pero backend aplica siempre `auth` + `password.change` + `verify.session` + permiso real.
2. Formulario en es-CL, usable por teclado y móvil. `receipt_paper` es un selector cerrado; encabezado/pie admiten texto o vacío. No exponer otras configuraciones, datos personales, secretos ni JSON general al frontend.
3. Guardar los tres valores normalizados en las filas `system_configs` existentes, sin sobrescribir claves distintas ni cambiar `is_secret`, `value_type` o esquema. Se permite utilizar el patrón `update`/upsert SOLO si mantiene el contrato y no crea claves arbitrarias; no correr seeds o migraciones remotas.
4. El guardado y la auditoría deben ocurrir en **la misma transacción**; registro `core.receipt_settings.updated`/equivalente con actor/fecha e identificación de las claves modificadas, **nunca el contenido completo del encabezado/pie** (podría incluir PII). Si falla auditoría, revertir todos los cambios.
5. Validar campos y permisos con pruebas: usuarios sin permiso = 403 (GET/PUT); entradas desconocidas/no válidas no se guardan; editar no toca configuraciones ajenas; valores siguen presentes tras lectura; auditoría sin contenido PII y con rollback ante fallo; comprobar restricciones RN-70 si aplica, sin crear política de gracia.
6. Ejecutar regresiones AUTH/BRANCH/USERS, suite PHP, TypeScript y Vite; QA independiente, `stockflash-publisher` AUTO_GIT y GitHub Actions por SHA. Incorporar gates **CFG-001** en `GATES_BY_PACKET` de `scripts/sf_verify.py` reutilizando infraestructura actual (sin nuevos scripts/agentes). Handoff `GUIA_PENDIENTE_CHATGPT` para textos del manual HTML, sin que OC los edite.

## Criterios EARS

- CUANDO un Admin Central con `settings.manage` abre los ajustes de comprobante, EL SISTEMA DEBE presentar los valores actuales de las tres claves y permitir editarlos.
- CUANDO el operador guarda un tamaño admitido y textos válidos, EL SISTEMA DEBE persistir exactamente estas claves y registrar auditoría atómica.
- CUANDO un usuario carece de `settings.manage`, EL SISTEMA NO DEBE permitir lectura ni escritura, aun por URL directa.
- CUANDO se envían claves extra, valores inválidos o falla la auditoría, EL SISTEMA NO DEBE persistir cambios parciales ni exponer secretos.
- CUANDO la instalación está bloqueada en modo solo lectura por una licencia suspendida fuera de gracia, EL SISTEMA NO DEBE permitir modificar la configuración (reutilizar la semántica contractual existente; no inventar suspensión).
