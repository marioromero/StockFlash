## Objetivo y resultado esperado
Incorporar a GitHub Actions una CI reproducible para el scaffold Laravel 13 / PHP 8.3 y Vue 3 / TypeScript / Vite / Node 24, sin usar credenciales del hosting ni desplegar a staging. Validar continuamente la rama main y pull requests antes de iniciar R3. Mantener intactos los workflows existentes.

## Alcance aprobado
1. Crear workflow CI de aplicación en `.github/workflows/`, con `pull_request`, `push` a `main` y `workflow_dispatch` (o equivalente que permita comprobar la ejecución real). `permissions: contents: read`, tiempos máximos y prevención de ejecuciones redundantes sin cancelar publicaciones críticas. Sin ambiente de deploy ni claves SSH.
2. Job PHP 8.3 en runner GitHub alojado: checkout, setup-php estable, extensiones necesarias (`mbstring`, `dom`, `xml`, `pdo_sqlite`, `fileinfo`), `composer validate`, instalación determinista con `composer install` desde `composer.lock` y `php artisan test`. No ejecutar migrate, seed ni acceso a MariaDB/staging; test unitarios/feature actuales. Ajustar solo configuración efímera de test si el runner carece de APP_KEY, sin publicar claves ni copiar datos reales.
3. Job frontend Node 24: checkout, setup-node, `npm ci` con `package-lock.json`, `npm run typecheck` y `npm run build`. Publicación opcional del artefacto `public/build` SOLO como artefacto de CI con retención corta (no como deploy), verificando exclusión de secretos y rutas dinámicas.
4. Gate smoke local/CI: validar GET `/` → 200, HTML `lang="es-CL"` y referencia a la aplicación Vue/Inertia, arrancando y deteniendo un servidor efímero en el runner. Reusar mecanismo determinista existente o implementar comprobación delimitada y reproducible; no conectar red externa ni bases de datos de producción.
5. Añadir `CI-001` al registro `GATES_BY_PACKET` de `scripts/sf_verify.py`, con gates que comprueben sintaxis/estructura workflow, política de permisos (sin `write`, ssh, deploy, migraciones), instalación y tests cuando sean pertinentes. El verificador debe producir `GATES_PASS` real; no falsear ejecución de GitHub Actions.
6. Crear documentación operativa `docs/harness/CI-001-OPERACION.md` breve: disparadores, permisos, señales verdes/rojas, ubicación de logs y artefactos, resolución de fallas y separación respecto de staging; no introducir procedimiento manual rutinario por feature.
7. Ejecutar QA independiente, incorporar reporte `CI-001-REVIEW-*.md` y publicación por publisher con staging explícito, diff-check, barrido de secretos y triple SHA. Confirmar en GitHub que el workflow corrió realmente y su resultado, antes de recomendar VERIFIED.
8. Reusar acciones oficiales vigentes y soporte de versiones comprobado. Priorizar referencias fijadas a SHA validado cuando sea factible; no inventar SHA de acciones ni relajar los permisos. Compatible con `composer.json`, `phpunit.xml` y `package.json` ya existentes. No agregar dependencias de aplicación salvo necesidad demostrada y aprobada.

## Restricciones y exclusiones
- No modificar `docs/product/*`, `AGENTS.md`, `docs/governance/CONSTITUTION.md`, `opencode.json`, decisiones ADR, lógica de dominio ni assets de BRAND-001.
- No ejecutar migraciones, seeders, operaciones de DB o comandos destructivos. Nunca copiar/leer `.env` local ni incorporar secretos a los logs/artefactos.
- No activar despliegue a cPanel ni tocar `.github/workflows/staging-ssh-check.yml` salvo diagnóstico de solo lectura. R2 staging tendrá packet independiente.
- No declarar CI funcionando solo porque YAML es válido: evidencia de ejecución de GitHub Actions y resultado final exigidos para VERIFIED.
- No resolver unilateralmente los ADR-01..06 ni diseñar schema de R3.
- No convertir `--auto` en capacidad para saltar permisos `deny`, QA, revisiones ni puertas.

## Criterios EARS de aceptación
- CUANDO se publica una modificación en `main` o PR, GitHub Actions DEBE ejecutar automáticamente validaciones PHP 8.3 + Node 24, con resultados visibles.
- CUANDO se instalan dependencias, el workflow DEBE usar lockfiles y fallar si están inconsistentes.
- CUANDO corren tests y build, DEBEN terminar exitosamente en GitHub Actions y registrar evidencia, sin infraestructura externa.
- CUANDO se ejecuta smoke, DEBE comprobar HTTP 200 y locale `es-CL` sobre servidor efímero y cerrar recursos al finalizar.
- CUANDO se inspeccionan permisos y logs, NO DEBEN existir permisos de escritura injustificados, secretos en artefactos ni acciones de despliegue/DB.
- CUANDO el pipeline falla, DEBE quedar un resultado FAIL trazable y una corrección concreta; no falsear gates.
- CUANDO el reviewer termina, DEBE entregar APROBADO/cambios necesarios con evidencias; publicación NO equivale a VERIFIED.
