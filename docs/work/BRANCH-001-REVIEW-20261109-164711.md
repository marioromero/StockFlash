## Hallazgos nuevos por severidad

### Mayor

**M-03 — El filtro de secretos por token exacto omite claves camelCase y permite almacenar credenciales en `settings` y en `audit_logs`.**

- `BranchRequest::isSensitiveKey()` y `AuditLogger::isSensitiveKey()` normalizan a minúsculas y comparan tokens separados por caracteres no alfanuméricos. Una clave camelCase no se separa: `authToken` → `authtoken`, `clientSecret` → `clientsecret`, `secretToken` → `secrettoken`; ningún token coincide con la lista.
- Sondeo real con reflexión sobre `BranchRequest::isSensitiveKey()`:
  - `shipping_cost` → permitida (correcto), `mapping` → permitida (correcto), `user_pin` → SENSIBLE, `api_key` → SENSIBLE, `secret_token` → SENSIBLE, `apiKey` → SENSIBLE.
  - `secretToken` → **permitida**, `authToken` → **permitida**, `clientSecret` → **permitida**.
- Prueba temporal end-to-end (eliminada al terminar): `POST /branches` con `settings={"secretToken":"valor-real"}`, `{"authToken":...}` y `{"clientSecret":...}` devolvió **sin errores**; los valores quedaron en `branches.settings` y en `audit_logs.new_values` (se observó `"settings":{"secretToken":"valor-real"}` en la auditoría).
- Impacto: contradice el packet («No almacenar secretos, credenciales, tokens...») y la regla de `audit_logs` sin secretos (Parte 2 §4.19). Es una regresión respecto del filtro por subcadena anterior, que sí bloqueaba estos nombres.
- Dirección de corrección sugerida: separar límites camelCase antes de comparar tokens (p. ej. insertar `_` entre minúscula→mayúscula) y aplicar la misma lógica en `BranchRequest` y `AuditLogger`, manteniendo la comparación por token exacto para no volver a rechazar `shipping_cost`/`mapping`. Añadir pruebas de `authToken`, `clientSecret`, `secretToken` (incluidas anidadas) y conservar las de falsos positivos.

### Menor

- **m-01 — BN3/BN4 siguen siendo comprobaciones estáticas eludibles.** `scripts/sf_verify.py` tiene el mismo fingerprint que en el ciclo 1 (11104f13…): BN3 busca subcadenas y BN4 cuenta `transaction(`/compara índices, sin validar cada endpoint ni el middleware por ruta. No se observó debilitamiento de gates; BN5–BN9 ejecutan pruebas, typecheck y build reales, que son la cobertura efectiva. Se mantiene como observación, no como bloqueo.
- **m-02 — Ambigüedad residual de código numérico.** Si un código de sucursal coincide con el ID de otra sucursal, prevalece el ID. La política «primero ID, luego code» está documentada y probada para el caso sin colisión; el caso colisión es un borde no cubierto. No es regresión de BRANCH-001.
