## Hallazgos por severidad

### Bloqueante

**B-01 — El límite `license_states.max_branches` se elude reactivando la sucursal desde `PUT/PATCH /branches/{branch}`.**

- `BranchRequest::rules()` acepta `is_active` también en edición (`sometimes|boolean`).
- `BranchController::update()` persiste `$data` completo, incluido `is_active`, **sin** llamar a `assertWithinBranchLimit()` ni a `lockForUpdate()`.
- `Branches/Form.vue` expone el checkbox «Sucursal activa» también al editar, por lo que el camino es alcanzable desde la UI oficial sin usar `/activate`.
- Reproducción real ejecutada durante la revisión con una prueba temporal (creada, ejecutada y eliminada; el working tree quedó igual): `max_branches=1`, 1 sucursal activa + 1 inactiva, `PUT /branches/{inactiva}` con `is_active=true` → **HTTP 302, sin errores de validación, `is_active=true`, 2 sucursales en total**. Se superó el máximo de 1 sucursal activa.
- Incumple el punto 4 del encargo y el criterio EARS «CUANDO el Admin Central reactiva una sucursal, EL SISTEMA DEBE verificar el límite de plan de forma transaccional»; además evita la atomicidad exigida.
- No se corrige en esta revisión. Dirección sugerida: excluir `is_active` de `update` (usar solo `/activate` y `/deactivate`) o validar la transición `false→true` con `assertWithinBranchLimit()` dentro de la transacción, incluyendo auditoría coherente.

### Mayor

**M-01 — La desactivación desde la edición elude confirmación, advertencia de última sucursal y evento de auditoría correcto** (misma causa raíz que B-01). El checkbox de edición permite pasar `is_active=false` sin `window.confirm`, sin la advertencia de última sucursal activa y registrando `branch.updated` en lugar de `branch.deactivated`. El packet exige confirmación/advertencia para desactivar y eventos exactos por tipo de operación.

**M-02 — Sin prueba para el enlace del dashboard ni para transiciones de estado por edición.** No hay test que verifique que el enlace «Sucursales» solo se comparte/visualiza con `settings.manage`, ni que cubra el bypass B-01/M-01. La suite verde no detecta el hallazgo bloqueante.

### Menor

**m-01 — Gates BN3/BN4 eludibles.** BN3 solo busca subcadenas (`/branches`, `can.permission:settings.manage`, `is_active`, `abort(403`) y BN4 solo cuenta `transaction(` y compara el índice del primer `transaction(` con el primer `auditLogger->log`. No validan que cada endpoint tenga su auditoría dentro de la transacción ni el middleware por ruta. BN5–BN9 sí ejecutan pruebas/build reales y complementan la cobertura; no hay evidencia de debilitamiento respecto del estado anterior.

**m-02 — `settings: []` como array real.** `settingsObjectRule` acepta el array vacío (`$value !== []` exime) y `normalizeSettings` solo convierte cadenas; un cliente JSON que envíe `settings: []` puede almacenar un arreglo JSON en lugar de un objeto. El test solo cubre la cadena `'{}'`.

**m-03 — Filtro de secretos por subcadena con falsos positivos.** Claves legítimas como `shipping` o `mapping` contienen `pin` y serían rechazadas; no es un problema de seguridad, pero sí de usabilidad/validación.

**m-04 — Ambigüedad de identificador numérico en `EnsureBranchAccess`.** Un código de sucursal puramente numérico se interpreta como ID (`is_numeric`). Es comportamiento preexistente de AUTH-001, no una regresión de BRANCH-001, pero el packet permite códigos numéricos.

**m-05 — Ajuste colateral en gate A1 de AUTH-001.** `scripts/sf_verify.py` relaja A1 para aceptar `status: VERIFIED`; es coherente con el estado committed de AUTH-001, pero es un cambio fuera del alcance estricto de BRANCH-001.
